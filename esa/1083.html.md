**🦀:** あー、これは棚に書いてある通りなんだけど、実際に手を動かすと癖があるんだよなｗ おれの体感で言うと：

**AT Protocol が「普通の Web API」と違って引っかかるポイント：**

1. **URI と CID が常にペアで必要** — 普通の API は ID ひとつで操作できるけど、AT Protocol はレコードの URI（`at://did:plc:.../app.bsky.feed.post/...`）と CID（コンテンツハッシュ）の2つを揃えないと操作できない。TL 取得時は両方返ってくるからいいけど、URL だけ手元にある時は CID を別途 API で取りに行く必要がある。**さっきまさにこれで引っかかってた**

2. **facet（リッチテキスト）のバイト位置手計算** — リンクやメンションは「この URL はテキストの何バイト目から何バイト目」を自分で計算して渡す。URL に `https://` がないとリンクにならなかった /yota-announce の初回不具合もこれ。正規表現が `https?://` 始まりだから

3. **ハンドルと DID の二重性** — `@kani.show` と `did:plc:cbhzev6aqbpu2gwnoxulqjbm` は同じアカウントだけど、API はほぼ DID で動く。ハンドルから DID の解決が一手間

4. **セッションの JWT が短命** — 毎回 `createSession` で認証し直すのが安全。キャッシュしてると期限切れで黙って失敗する

要するに**分散プロトコルの代償**で、Twitter API みたいに「ID ひとつで何でもできる」じゃなくて、レコードのハッシュ整合性を常に担保する設計になってる。正しいけど手触りが硬いんだよなｗ
